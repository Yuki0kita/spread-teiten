# スプレッド定点

国内の暗号資産取引所のビットコインのスプレッドを、**1分ごとに実測して記録し続ける**サイト。

見せるのは1つだけ。

> この金額を、いま買って、すぐ売り戻したら、どこでいくら消えるか。

- 画面: `/{lang}/{pair}/` と `/{lang}/{pair}/{YYYY-MM-DD}/`
- データ: `/api/latest.json` `/api/history.json` `/api/daily.json`（いずれも `?pair=btc|eth|xrp`）
- 実測ロジック: [src/spread.ts](src/spread.ts)

## ページの構成

```text
/                          → ブラウザの言語を見て /ja/ か /en/ へ
/{lang}/                   銘柄の一覧
/{lang}/{pair}/            その銘柄の現在値と24時間の推移
/{lang}/{pair}/{date}/     その日の記録
```

`lang` は `ja` `en`、`pair` は `btc` `eth` `xrp`。

日別ページは**記録が貯まるだけ自動で増える**。手を動かさずにページが増えるのはここだけなので、
日付の前後リンクと `recentDays` の一覧を必ず置いてクロールの導線を切らさない。
記録の無い日付は404を返す。中身の無いURLを生やすとサイト全体の評価を落とすため。

言語はパスに置く。`?lang=ja` のようなパラメータ方式は検索エンジンが別ページとして
扱いにくいため使わない。全ページに `hreflang`（ja / en / x-default）と `canonical` を出している。

## なぜ作ったか

「仮想通貨 スプレッド 比較」で上位に出てくるのは、どれも**編集部が調べた静的な表**だった。
そしてその数字は実測と合っていない。

2026年8月25日 14:10 に4取引所の公開APIから同時に取得した実測値。

| 取引所 | 実測スプレッド | 比較記事の記載 |
|---|---:|---|
| GMOコイン | 0.00047% | 「取引所形式はほぼ0.01%」 |
| bitbank | 0.022% | 同上 |
| bitFlyer | 0.028% | 同上 |
| Coincheck | 0.032% | 同上 |

さらに9時間後の23:50にはGMOとbitbankが1円差（0.0000079%）まで縮み、bitFlyerは0.03%のままだった。
**スプレッドは固定値ではなく、時間帯と板の状態で数十倍動く。** その推移を記録している場所が無かった。

「いまいくらか」は各取引所のサイトを見れば分かる。誰も持っていないのは**時系列**のほうなので、
このサイトの資産は画面ではなく、貯まっていくデータベースにある。

## 数字の定義

```text
往復コスト（円） = 購入額 × (ask − bid) ÷ ask
スプレッド（bps）= (ask − bid) ÷ 中値 × 10,000
```

買うときは売値(ask)で約定し、売るときは買値(bid)で約定する。
手元に戻るのは `購入額 × bid ÷ ask` なので、その差額がスプレッドで失う金額になる。

## 表示しないもの

このサイトの数字は**すべて実測値**で、推定や公表値を混ぜていない。そのため次は出さない。

- **取引手数料・入出金手数料**。APIから取れないため含めていない
- **販売所のレート**。公開APIから取得できない。扱っているのは取引所形式（板取引）の気配値だけ
- **おすすめの取引所**。特定の取引所をすすめるものでも、投資判断を助言するものでもない

## 仕組み

```text
Cloudflare Cron（毎分）＋ GitHub Actions（5分ごと・予備）
   ↓ 4取引所の公開APIを並列で取得（同じ瞬間の値であることが比較の前提）
   ↓ 気配値の妥当性チェック（ask < bid や 20%超は捨てる）
D1
   ├─ ticks    生の観測値（14日で削除）
   ├─ buckets  10分足（グラフはここから144点だけ読む）
   └─ daily    日次集計（10分足からsamplesで重み付けして積む）
   ↓
Workers + Hono（SSR）→ 画面とJSON
```

集計をCron側で先に済ませているのは、画面が読む行数をD1の無料枠に収め続けるため。
1画面あたり600行程度しか読まない。

## 取得元

いずれも認証不要の公開APIで、板の最良気配を返す。

| 取引所 | エンドポイント | 銘柄の指定 |
|---|---|---|
| GMOコイン | `https://api.coin.z.com/public/v1/ticker` | `?symbol=BTC` |
| bitbank | `https://public.bitbank.cc/{pair}/ticker` | `btc_jpy` |
| bitFlyer | `https://api.bitflyer.com/v1/ticker` | `?product_code=BTC_JPY` |
| Coincheck | `https://coincheck.com/api/ticker` | `?pair=btc_jpy` |

扱う銘柄は**4社すべてが板を公開しているもの**に限っている（BTC・ETH・XRP）。
2社しか対応していない銘柄を並べても比較として意味が薄い。
増やすときは [src/pairs.ts](src/pairs.ts) に足す前に、必ず全社のエンドポイントを実際に叩いて確かめる。
bitFlyerは未対応の銘柄に `{"status":-100,"error_message":"Invalid product"}` を返す。

bitbankだけ名前が直感と逆で、`sell` が売り注文の最安値（= 買う値段 = ask）、
`buy` が買い注文の最高値（= 売る値段 = bid）。取り違えると `ask < bid` になって全データが捨てられるため、
[tests/venues.test.mjs](tests/venues.test.mjs) で固定してある。

各取引所へのリクエストは1分に1回ずつ。負荷にならない頻度に抑えている。

## 公開する

Node 22以上が必要（テストが `.mjs` から `.ts` を直接importするため）。

```bash
export PATH=~/.nvm/versions/node/v22.23.2/bin:$PATH
```

### 1. Cloudflareにログインする

ブラウザが開いて承認を求められる。

```bash
npx wrangler login
```

### 2. D1を作る

```bash
npx wrangler d1 create spread_teiten
```

出力された `database_id` を `wrangler.jsonc` の `PLACEHOLDER_RUN_WRANGLER_D1_CREATE` と差し替える。

```bash
npm run db:init:remote
```

### 3. デプロイ

```bash
npm run deploy
```

Cronの設定は `wrangler.jsonc` に残してあるが、いまは発火していない（次節）。

### 4. 公開後に確認する

```bash
curl -s https://spread-teiten.teiten.workers.dev/api/errors.json
```

Search Consoleに `https://spread-teiten.teiten.workers.dev/sitemap.xml` を登録する。
OGPは実際にXへURLを貼ってプレビューを確認する（`/og.png` が1200×630で出る）。

## 観測を動かす経路が2つある理由

CloudflareのCron Triggerは、登録されていても発火しないことがある。
このプロジェクトでも公開直後に実際に起きた（`schedule: * * * * *` と表示され、
`wrangler triggers deploy` で再登録しても、30分以上まったく発火しなかった。
`wrangler dev --remote --test-scheduled` で同じ処理を叩くと1.5秒で成功するので、コード側の問題ではなかった）。
その後、こちらが何もしないまま自然に発火し始めた。**いつまた止まるか分からない**ということなので、
予備の経路は残してある。

スケジューラが1つしかないと、黙って止まったときにデータが欠け続ける。
そこで収集本体を [src/collect.ts](src/collect.ts) に出し、HTTPからも叩けるようにしてある。

```bash
curl -X POST -H "Authorization: Bearer $COLLECT_TOKEN" \
  https://spread-teiten.teiten.workers.dev/internal/collect
```

- トークンは Worker のシークレット `COLLECT_TOKEN`。`npx wrangler secret put COLLECT_TOKEN` で登録する
- トークンが合わないときは401ではなく**404**を返す。存在を知らせない
- `COLLECT_TOKEN` が未設定なら、この経路ごと無効になる（フェイルクローズ）
- 同じ分に何度呼ばれても行は増えない。`ts` を分単位に丸めた `INSERT OR REPLACE` なので上書きになる

Cronの設定は消していない。Cloudflare側が直れば1分間隔に戻せる。そのときはサイトの文言も戻す。

## D1の読み取り予算

このサイトはJSONを誰でも叩けるようにしてあるので、素直に作るとアクセスがそのままD1の読み取りになる。
少し連打されただけで1日の無料枠（読み取り500万行）が飛び、その日1日サイトが死ぬ。

そのため、D1の結果自体をエッジのキャッシュに置いている（[src/cache.ts](src/cache.ts)）。
キャッシュキーに時刻を量子化して埋めてあるので、観測が更新される間隔でだけ作り直る。

| 読み取り | 1回の行数 | 作り直す間隔 | 1日の行数 |
|---|---:|---|---:|
| 最新の気配値 | 4 | 1分 | 5,760 |
| 10分足（グラフ） | 576 | 10分 | 82,944 |
| 日次集計 | 〜720 | 1時間 | 17,280 |

合計およそ10万行で、アクセス数によらずほぼ一定になる。無料枠の2%程度。

ただし Workers のキャッシュは**データセンターごと**に持つため、
アクセスが世界中に散ると、その拠点の数だけ読み取りが増える。
国内向けのサイトなので当面は問題にならないが、上限に近づいたらこの数字を疑う。

最新の気配値は取引所ごとに `ORDER BY ts DESC LIMIT 1` で引いている。
期間で絞る書き方にすると、Cronが止まったときに画面が「観測データがありません」になってしまう。
古い値を隠すのではなく、出したうえで何分止まっているかを画面に書く。

## 分かっている限界

- **観測は1分ごと**。その間のスプレッドの動きは見えない。板が薄い時間帯の一瞬の拡大は取りこぼす
- **bitFlyerはCloudflareの経路からだと503を返すことがある**。手元からは10回叩いて10回成功するので、
  Workersの出口IPが弾かれていると見ている。5xxは一度だけ取り直すようにしたが、それでも欠測は残る。
  日別ページの「観測数」列に取引所ごとの実際の件数を出しているので、そこで確かめられる
- **最良気配だけを見ている**。大きな金額を成行で入れると板を食って実効価格はもっと悪くなる。
  表示している往復コストは「板の一番上で約定できたら」という最良ケース
- **取得に失敗した瞬間は欠測になる**。隠さず `fetch_errors` に残し、`/api/errors.json` で見られるようにしてある
- **BTC・ETH・XRPのみ**。LTCやSOLはGMOとbitbankにはあるがbitFlyerに無いため、4社比較にならない

## 収益化について

このサイトに「この取引所がおすすめ」という文言を置かない。行儀の問題ではなく規制の線引きの問題で、
2026年施行の改正資金決済法により「電子決済手段・暗号資産サービス仲介業」の登録制度ができている。

単なる情報提供やリンク掲載は直ちには登録対象にならないとされるが、
特定の者に契約締結へ向けた誘引行為を行っていると評価できる場合は媒介にあたりうる。
事実（観測値）だけを出すという方針は、この線の内側に留まるための設計でもある。

## これから

作る前に増やさない。まずデータを貯めて、アクセスと反応を見てから決める。

- **取引所別ページ**（`/{lang}/venues/{venue}/`）。銘柄×取引所でさらにページが増える
- 「暴落した日にどこが何倍に開いたか」を日次データから出す。実測でしか書けない記事になる
- 取引手数料を加えた実効コスト。公表値を持ち込むことになるので、実測値と混ざらないよう表示を分ける
- 被リンク。中身が増えてからでないと効かないので、日別ページが貯まってから

## 出どころ

SNSで見かけた「『仮想通貨取引所スプレッド最新比較』はツールが不在だから、作れば上位表示できる」という
指摘がきっかけ。1年半後に確認したところ、実測ツールも時系列データも見当たらなかったので作った。
